Let Postgres do the math

An analytics assistant that writes SQL instead of guessing numbers, and the eval suite that keeps it honest.

CT Chau Tieu · Drafted with AI, edited by me

Ask a language model how long your pull requests take to merge and it will give you an answer. It will sound right, it will be well formatted, and there is no way to tell whether it is true. For a metrics tool that is the only property that matters, so delivery-metrics is built around one rule: the model never does arithmetic.

1The problem with asking a model for numbers

A model that reads raw rows and summarises them is doing two jobs at once: understanding the question and computing the answer. It is good at the first and unreliable at the second, and the failure is silent. A median that is off by a few hours looks exactly like a correct one.1

1Not a criticism of any particular model. Arithmetic over thousands of rows is simply the wrong job for a text predictor.

2The model writes queries; the database does the arithmetic

Instead of handing the model data, delivery-metrics hands it a schema. Its only output is SQL. Postgres runs the query and returns rows; the model then explains the result in plain language, with the query attached so anyone can check it.

The query runs as a database role that can read and do nothing else.2 That single grant is the whole safety model: no prompt has to be trusted to behave.

2A read-only role turns a bad query into a wrong answer, not a damaged database. A wrong answer can be caught by a test.
roles.sql SQL
1CREATE ROLE analyst_ro NOLOGIN;
2GRANT USAGE ON SCHEMA metrics TO analyst_ro;
3GRANT SELECT ON ALL TABLES IN SCHEMA metrics TO analyst_ro;
4ALTER ROLE analyst_ro SET statement_timeout = '5s';
5
6-- every model-generated statement runs as this role
7SET ROLE analyst_ro;
Illustrative SQL. The highlighted line is the one that matters.

Zoomed out, the system has four moving parts. The sync worker is the only one that writes to the database; the assistant is the only one that talks to the model, and it holds the narrowest grant.

3Testing a model like a system

Around 730 unit tests cover the code around the model. None of them can tell you whether the assistant answers questions well. For that the project keeps a graded evaluation suite: 53 questions with known answers, run against the same database the assistant uses.3

3The suite lives next to the tests, so changing a prompt is reviewed like changing code.
eval/grade.py Python
1from dataclasses import dataclass
2
3@dataclass(frozen=True)
4class EvalCase:
5 question: str
6 expected: float
7 tolerance: float = 0.01
8
9def grade(case: EvalCase, answer: float) -> bool:
10 """Pass only if the number matches what Postgres computed."""
11 return abs(answer - case.expected) <= case.tolerance
Illustrative, not the project’s code. A case passes only when the assistant’s number matches the database.

If a number cannot be traced to a query, it does not belong on the dashboard.
