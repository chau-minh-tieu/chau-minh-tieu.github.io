## 1. Context

**What this is.** A personal portfolio and technical blog for Chau Tieu, published at `https://chau-minh-tieu.github.io` from the public repository `chau-minh-tieu/chau-minh-tieu.github.io`. It is a static site: Astro builds it, GitHub Actions deploys it, GitHub Pages serves it. There is no server, no database, no analytics and no third-party runtime service.

**What it is for.** The site is the owner's notebook: what he learns about software, data, AI and engineering leadership, written down properly. It doubles as a quiet portfolio. Tagline: *"Notes on software, data & AI, and engineering leadership."* Language: English only.

**How posts get written.** Post drafts are generated by AI. The owner writes a brief (including the insight only he can supply), an AI drafts the post as a Markdown file on a branch, the owner reviews the pull request line by line, and merging publishes. Section 6 specifies this workflow; building its tooling is part of the scope.

**How the owner works.** The owner writes no code. You write a one-page brief per feature, the owner approves it, you build it, and you hand back a debrief that teaches what was built. The owner is a senior backend engineer and engineering manager (Java, Python, ML, system design), newer to frontend, Astro and CSS. Explain frontend decisions properly; keep backend basics brief.

**Time budget.** The whole build fits in **4–6 hours of the owner's time on one day**, including reading, reviewing, waiting for builds and discussion (section 8).

## 2. Working agreement

1. **Feature loop.** For each feature in section 8:
   1. **Brief** in `docs/features/NN-slug.md`, one page at most: purpose, what the owner will learn (3–5 concepts tagged `[Astro]`, `[CSS]`, `[TS]`, `[Content]`, `[CI/CD]` or `[GitHub]`), numbered decisions each with a recommended default, acceptance criteria, timebox. The owner replies "go" or adjusts.
   2. **Build** on branch `feat/NN-slug`. Stop mid-build only if continuing would breach a guardrail (section 3), make a change that cannot be undone, or contradict an approved decision. Otherwise decide, proceed, and record the decision in the debrief.
   3. **Checks:** typecheck, build, tests, privacy check all green locally. Never hand back a red build; if something cannot be fixed, say so at the top of the message.
   4. **PR** with `gh` (title `feat(NN): …`, body links the feature doc, screenshots of UI changes if a headless browser is available locally). The owner merges.
   5. **Debrief**, appended to the same feature doc (section 7). ~~It ends with the brief for the next feature, so one owner reply can close one feature and open the next.~~ *Owner decision, 2026-10-25: one feature per chat. The feature's chat checks the draft brief against current docs, revises it on the feature branch and waits for "go"; builds, runs the checks, opens the PR with screenshots and appends the debrief, whose "Next" only names the next feature. Then it waits while the owner reviews the PR, answers questions in the teaching style and logs them in the debrief's Q&A on the PR branch. On "review done" it gives the merge command (`gh pr merge <N> --squash --delete-branch`) and never merges itself. After the merge it verifies read-only (local `main` equals `origin/main` at the squash commit, clean working tree, branch deleted, the `main` ruleset still applies) and ends with a copy-paste prompt that starts the next feature's chat in the same loop.*
2. **Batched questions.** Ask every open question in one message, numbered, each with a default and a one-line reason. "defaults" accepts all.
3. **GitHub setup guides.** When the owner must act in GitHub's UI, give one numbered guide: exact click path, the expected end state, and the equivalent `gh` command. After the owner confirms, verify with read-only `gh api` calls. The owner always enters secret values; never ask for them in chat.
4. **Time checkpoints.** Report elapsed time against the budget in every debrief. ~~If the site is not live by 2 h 30 min, or F5 is not done by 4 h 15 min, propose concrete cuts from the stretch list before starting the next feature.~~ *Owner decision, 2026-10-25: the budget may run over. Nothing is scoped down at checkpoints; features run in the order of section 8.*
5. **Discussion within budget.** Answer questions in the teaching style of section 7 and log them in the feature's Q&A. If a question deserves a deep dive that would blow the timebox, answer briefly and park it in `docs/deep-dives.md`.
6. **Freshness.** Check current official docs for anything version- or feature-dependent before writing a brief, cite links, use the latest stable versions at scaffold time and pin them.

## 3. Guardrails

### 3.1 Privacy (non-negotiable)

The repository is public. Code, docs, content, commit messages, branch names, PR titles and bodies, and issue text are all public.

**Allowed personal information** (and only this):

| Item | Value |
|---|---|
| Name | Chau Tieu (GitHub username `chau-minh-tieu`) |
| Role | Engineering manager |
| Career summary | The About copy in section 5.3, verbatim |
| Places | "Vietnam and Singapore", country level only |
| Links | `https://github.com/chau-minh-tieu`, `https://www.linkedin.com/in/tieuminhchau`, `https://www.reignedge.com` |
| Side venture | "Reign Edge, an AI-native trading platform, a side project" and nothing more |
| Interests | The single travel sentence in section 5.3 |
| Identity mark | The CT monogram; no photographs of the owner |

**Never in the repository:** names of current or past employers or clients; cities, addresses or phone numbers; **any email address** (the site publishes none); CV content beyond the About copy; internal figures from any employer; colleagues or identifiable people; trading positions, results or personal trading vehicles; Reign Edge internals, roadmap or strategy beyond the one-line description.

**If the owner shares real-world context** to explain something, use it for understanding only and translate it into generic terms before anything reaches the repository. If unsure whether something is allowed, ask.

**Privacy check.** `scripts/privacy-check.ts` scans tracked files and PR commit messages for terms in a local, gitignored `.privacy-terms` file and, in CI, the `PRIVACY_TERMS` secret. It never prints a matched term: file, line and term index only. It runs as a pre-commit hook and in the PR workflow, and skips cleanly when the secret is unavailable (fork PRs).

**Images.** Strip EXIF and GPS metadata from every image at build time; verify that the image pipeline does it and add a test.

### 3.2 Repository and Git

- Never push to `main`, force-push, merge PRs, change repository settings or visibility, or delete branches you did not create. Configure `.claude/settings.json` to deny these, allow read-only commands (`git status`, `git diff`, `git log`, `gh pr view`, `gh run view`, `gh api` GET), leave everything else on ask. Verify the current permission-rule syntax.
- The owner applies repository settings from your setup guides.
- Conventional commits. Commits use the owner's GitHub no-reply email. Never commit secrets, `.privacy-terms` or `.env*`.

### 3.3 GitHub Actions security

- Only actions created by GitHub (`actions/*`, `github/*`). If a third-party action seems necessary, stop and ask; prefer a script.
- Never `pull_request_target`; never use `workflow_run` to give PR code write access.
- Never interpolate untrusted event data (issue or PR titles and bodies, branch names, commit messages) into `run:` scripts; pass it through `env:`.
- Least-privilege `permissions:` per job, default `contents: read`.
- Every job uses `runs-on: ${{ vars.RUNNER || 'ubuntu-latest' }}`.
- Deploys happen only from `main` through the `github-pages` environment, restricted to the default branch.

### 3.4 Frontend security

- No third-party scripts, stylesheets, fonts or CDNs at runtime. Self-host fonts from npm. No analytics, no cookies.
- Render content as text; no `dangerouslySetInnerHTML`-style escapes for user-controlled strings. Sanitise rendered Markdown, because post bodies may contain raw HTML.
- Ship a Content Security Policy through `<meta http-equiv>`, starting from `default-src 'self'`; document and justify every relaxation (for example inline styles from rendered SVG, or a hashed inline theme script).

## 4. Architecture and technical decisions

### 4.1 Architecture

```
GitHub issue "Post brief"  ──▶  AI drafts on branch post/<slug>  ──▶  PR (CI gates)
                                                                      │ merge
                                                                      ▼
src/content/posts/<slug>/index.md + images ──▶ astro build ──▶ dist/ ──▶ GitHub Pages
```

### 4.2 Fixed decisions

Change any of these only after asking.

| Concern | Choice |
|---|---|
| Framework | Astro (latest stable), static output, TypeScript `strict` |
| Packages | Node active LTS, pnpm via corepack, single package |
| Content | Astro content collections with a Zod schema (section 6.2); posts are **`.md`, not `.mdx`**, so GitHub's PR preview matches the site |
| Code highlighting | Shiki at build time with a **custom theme built from the code tokens in section 5.1**; file name, line numbers and highlighted lines via fence meta (`title="roles.sql" {7}`) and Shiki transformers; a copy button from one small self-hosted script |
| Diagrams | Rendered to **SVG at build time**, themed with the figure palette for light and dark mode; no diagram JavaScript at runtime (decision in F4) |
| Interactivity | None by default. Only the theme toggle and copy buttons ship JavaScript; Astro islands only if a feature truly needs one |
| Styling | Plain CSS with custom properties for every token (section 5.1); no CSS framework unless you make a strong case in F1 |
| Fonts | Inter (variable, with optical sizes) and JetBrains Mono from `@fontsource`, self-hosted, OFL |
| Feeds and SEO | RSS, sitemap, canonical URLs, Open Graph and Twitter meta, `noindex` on unlisted posts |
| Testing | Vitest for utilities and remark/rehype plugins; a build-output test asserting privacy and metadata rules |

### 4.3 Proposed defaults (confirm at kickoff)

- **Diagrams:** Mermaid rendered at build time (for example `rehype-mermaid` with a headless browser in CI) for flowcharts, sequence and C4 diagrams, with `themeVariables` mapped to the figure palette. Compare with D2 (CLI in CI) and with pre-rendering SVGs locally and committing them. Fallback if the CI browser costs too much time: pre-rendered SVGs.

- **Tag filtering:** tag chips on the home page are plain links to static `/tags/<tag>/` pages, not client-side filters.

## 6. Content model and workflow

### 6.1 Authoring conventions

- One folder per post: `src/content/posts/<slug>/index.md`, images beside it.
- Footnotes (`[^1]`) render as sidenotes on wide screens and as notes below the paragraph on phones; GitHub's preview still shows them as footnotes.
- GitHub alerts (`> [!NOTE]`, `> [!TIP]`, `> [!WARNING]`) render as notes.
- Fenced code with meta: ```` ```sql title="roles.sql" {7} ````.
- Mermaid diagrams in ```` ```mermaid ```` fences; a caption convention for figures (propose one that also reads well in GitHub's preview).
- Images: Markdown image syntax with alt text required; a title becomes the caption.

### 6.2 Frontmatter schema

| Field | Rule |
|---|---|
| `title` | required, ≤ 120 chars |
| `description` | required, ≤ 160 chars (dek, meta description, RSS) |
| `pubDate`, `updatedDate` | dates |
| `tags` | 1–2 of `engineering`, `ai`, `leadership`; the first is primary and sets the accent |
| `status` | `draft` (never built in production) · `unlisted` (built, `noindex`, excluded from lists, tags, RSS and sitemap; for previewing on the live site) · `published` |
| `brief` | the issue number of the post brief |
| `sources` | list of `{ title, url }`; required when `tags` includes `engineering` or `ai` |
| `aiAssisted` | boolean, default `true`; drives the disclosure line |
| `disclosure` | optional override of the disclosure sentence |

### 6.3 Workflow

1. **Brief.** The owner opens an issue from `.github/ISSUE_TEMPLATE/post-brief.yml`: working title, thesis, audience, **insight (required: what the owner learned, decided, measured or got wrong)**, rough outline (optional), must include, do not include (categories only, never real names), sources. Label `brief`.
2. **Lock.** `lock-briefs.yml` locks brief issues on creation so only collaborators can comment; brief threads become AI input, and outside comments would be a prompt-injection channel. Issue creation is restricted to collaborators in Setup Guide A.
3. **Outline, then draft.** An AI (Claude Code locally for now) proposes an outline as an issue comment; after the owner approves, it drafts the post on `post/<slug>` with `status: unlisted` and opens a PR containing `Closes #<brief>`.
4. **Gates in CI** for post PRs: build and schema validation; privacy check; **scope check** (a `post/*` PR may change only `src/content/posts/**`); link check (script or maintained npm tool, no third-party action); alt text present; sources present when required.
5. **Review and preview.** The owner reviews the rendered Markdown diff; for a full-fidelity check, merge as `unlisted`, view the live URL, then flip to `published` in a follow-up PR.
6. **Publish.** Merge; deploy; the brief issue closes.

**`STYLE.md`** (written in F6) tells the drafting AI how to write: plain words, concrete specifics, the owner's insight at the centre, no filler, no closing recaps, no AI tropes ("it's worth noting", "in today's fast-paced world", "delve", "not X, it's Y"), sources for every technical claim and number, numbers only from verifiable personal sources, leadership posts as composite and time-shifted lessons with no identifiable people, no trading positions or results, and the privacy rules of section 3.1.

## 7. Documentation and teaching style

- `CLAUDE.md` (F0): standing rules distilled from this document.
- `docs/00-plan.md` (F0): architecture, decisions with alternatives and recommendations, versions with links, numbered open questions with defaults. Two pages at most.
- `docs/features/NN-slug.md`: **Brief** before the build; **Debrief** after it:
  1. What was built (Mermaid diagram when a flow is involved).
  2. File tour: each file's single responsibility and dependencies.
  3. Concepts: mental model, how it is used here (with paths), 1–3 common mistakes, official doc link.
  4. Verify it yourself: commands or pages and what correct output looks like.
  5. Check your understanding: three questions, answers in `<details>`.
  6. Deviations and gotchas.
  7. Time used: this feature and cumulative, against the budget.
  8. Q&A log.
  9. Next: ~~the brief for the next feature~~ the next feature's name; its own chat writes the brief (owner decision, 2026-10-25, section 2.1).
- `docs/runbook.md` (F7): publishing a post end to end, unpublishing, rolling back a deploy.

Teaching style: mental model before mechanics; anchor new ideas to what the owner knows (an Astro page ↔ a server-side template rendered once at build time; a content collection ↔ a typed table validated by a Pydantic-like schema; remark/rehype ↔ a compiler pipeline of AST transforms; CSS custom properties ↔ configuration injected at runtime; the Pages artifact ↔ a container image built from a larger build context). Direct and concise; tables for comparisons.
